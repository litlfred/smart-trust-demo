Chaque table indique les tâches de processus métier qu’elle sert, les exigences qu’elle applique, les éléments de données qu’elle lit et les artefacts FHIR qui l’illustrent dans les exemples.     Les sources sont processes/content/decisions/*.dmn ; cette page et les PlanDefinitions sont générées à partir d’elles. Les entrées utilisent le sous-ensemble FEEL qu’accepte l’interpréteur de tables de décision du harnais : - (tout), littéraux, comparaisons et « l’un de ». La politique de résultat de chaque table est FIRST : les règles sont essayées dans l’ordre et la première qui correspond s’applique ; l’ordre fait donc partie de la logique. Lorsqu’une règle indique « selon la politique nationale », il s’agit de la politique du pays de résidence ; les tables illustrent les décisions, elles ne sont pas les règles d’un pays.

    TD.DT.01 Que devient un DVC scanné dans le dossier de l’enfant ?

    À partir du résultat de la lecture d’un DVC étranger, décider si sa dose est enregistrée comme vérifiée, conservée comme déclarée et non vérifiée, ou pas du tout enregistrée à partir de celui-ci.

    • Au service de : J2 Repérer et orienter un nourrisson non enregistré dans le Pays B : Lire chaque DVC sans vérification (triage) (Task_Read) ; Ajouter le nourrisson ; enregistrer les doses comme déclarées (Task_Register) ; J3 Vérifier, importer et planifier au centre de santé du pays de résidence : Vérifier chaque HCERT par rapport à la liste de confiance (Task_Verify) ; Tous les DVC sont-ils vérifiés ? (Gateway_Verified) ; Noter l’échec ; décider des doses selon la politique (Task_Unverified) ; Importer les doses en tant que ressources FHIR Immunization (Task_Import)
    • Exigences : STT-VER-001, STT-VER-006, STT-VER-008, STT-VER-011
    • Éléments de données : TD.J3A.DE05 Résultat de la vérification, TD.J3A.DE07 Motif de l’échec, TD.J3A.DE09 Issue de l’enregistrement
    • Dans les exemples : StructureDefinition TrustDemoOnesaReportedImmunization, StructureDefinition TrustDemoOnesaDvcVerification, Provenance TrustDemoJ3Verification
    • Forme calculable : PlanDefinition TrustDemoDT01 ; source dvc-record-outcome.dmn, politique de résultat FIRST
    # Résultat de la vérification (result) Motif de l’échec (failureReason) Issue de l’enregistrement (outcome) Action (action) Annotation
    1 unverified tout reported-unverified Enregistrer la dose comme déclarée par la famille (primarySource false, l’aidant comme source d’information, une note indiquant que rien n’est vérifié) et orienter l’enfant vers le centre de santé pour vérification. Lecture de triage par le CHW dans J2 (STT-VER-011) : rien n’est vérifié, donc la dose est déclarée, jamais vérifiée. Exemple Immunization TrustDemoJ2HepBReported.
    2 verified tout verified Importer la dose avec primarySource true et une Provenance de vérification qui nomme la clé du signataire et supprime la dose déclarée qu’elle remplace ; puis faire correspondre son code de vaccin (TD.DT.02). Branche « oui » de J3 (STT-VER-001) : la dose est enregistrée à partir de sa source primaire. Exemples Immunization TrustDemoJ3HepB et Provenance TrustDemoJ3Verification.
    3 failed KidNotFound reported-unverified Conserver la dose comme déclarée ; consigner l’étape et le motif (STT-VER-008) ; vérifier à nouveau le DVC après la prochaine actualisation de la liste de confiance. Le certificat du signataire ne figure pas dans la liste de confiance en cache du centre de santé (STT-VER-006), par exemple un signataire ajouté après la dernière actualisation : la branche « non » de J3, « jusqu’à la prochaine actualisation ».
    4 failed l’un de Expired, NotYetValid reported-unverified Conserver la dose comme déclarée ; consigner l’étape et le motif ; le clinicien décide selon la politique nationale s’il faut administrer ou répéter la dose. La signature a été vérifiée, mais le certificat est en dehors de sa période de validité. La dose n’est pas vérifiée ; le clinicien décide selon la politique nationale.
    5 failed l’un de BadPrefix, UnsupportedContextVersion, Base45Invalid, InflateFailed, LimitExceeded, CoseMalformed not-read Scanner à nouveau ; en cas de nouvel échec, traiter la carte comme du papier et consigner pourquoi elle n’a pas été vérifiée. Le décodage a échoué avant toute vérification de signature (ordre de STT-VER-001), donc rien n’a été lu : trois états, et non deux, car un scan défectueux ne constitue une preuve ni dans un sens ni dans l’autre.
    6 failed tout rejected Ne pas enregistrer de dose à partir de ce certificat ; consigner l’étape et le motif ; le clinicien décide selon la politique nationale, comme pour une dose non documentée. Tout autre échec (signature, usage de la clé, en-tête, algorithme, revendication hcert ou charge utile) : le certificat ne constitue pas une preuve de dose.

    TD.DT.02 Quel code du calendrier national une dose importée porte-t-elle ?

    Pour une dose, décider si et comment le code du calendrier national est ajouté à côté du code de produit de l’émetteur, qui est toujours conservé.

    • Au service de : J3 Vérifier, importer et planifier au centre de santé du pays de résidence : Ajouter les codes nationaux à côté des codes étrangers (Task_Map)
    • Exigences : STD-SEM-001
    • Éléments de données : TD.J3A.DE09 Issue de l’enregistrement, TD.J3B.DE01 Code de produit de l’émetteur, TD.J3B.DE02 Code du calendrier national, TD.J3B.DE03 Fondement de la correspondance
    • Dans les exemples : ConceptMap TrustDemoProductToOnesaEpi, Provenance TrustDemoJ3Adjudication, Immunization TrustDemoJ3HepB
    • Forme calculable : PlanDefinition TrustDemoDT02 ; source vaccine-code-mapping.dmn, politique de résultat FIRST
    # Issue de l’enregistrement (TD.DT.01) (outcome) Entrée dans la table de correspondance nationale (mapEntry) Le clinicien confirme un équivalent (clinicianConfirms) Fondement de la correspondance (mappingBasis) Action (action) Annotation
    1 l’un de reported-unverified, rejected, not-read tout tout not-imported Aucun code de calendrier n’est ajouté. Seule une dose vérifiée est importée et mise en correspondance (branche « oui » de J3) ; une dose déclarée conserve uniquement le code de l’émetteur.
    2 verified equivalent tout concept-map Ajouter le code de calendrier correspondant à côté du code de produit. STD-SEM-001 (correspondance) : la table de correspondance nationale publiée comporte un équivalent ; les deux codages sont conservés, comme dans TrustDemoJ3Bcg.
    3 verified none yes clinician-confirmed Ajouter le code de calendrier confirmé à côté du code de produit ; consigner l’attestation du clinicien sous forme de Provenance ; ajouter la paire à la table de correspondance nationale. La table de correspondance n’a pas d’entrée et la clinicienne confirme l’équivalent (J3 : le produit hépatite B). Sa décision est consignée et ajoutée à la table de correspondance afin que le centre de santé suivant n’ait pas à la répéter.
    4 verified none no unmapped Conserver le code de produit tel quel et présenter la dose au clinicien comme sans correspondance ; le calendrier ne la compte pas (TD.DT.03). STD-SEM-001 (sans correspondance) : aucun équivalent n’est connu, et aucun n’est deviné.
